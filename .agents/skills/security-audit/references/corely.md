# Corely trust boundaries

Read [AGENTS](../../../../AGENTS.md), [architecture boundaries](../../../../docs/architecture/BOUNDARIES.md),
[persistence policy](../../../../docs/architecture/DATABASE_PERSISTENCE_STRATEGY.md) and
[repository evidence](../../../../docs/products/corely/repository-alignment.md).
These are audit starting points and required invariants, not findings or claims of universal enforcement.

| Boundary                        | Concrete audit questions and source entry points                                                                                                                                                                                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity and workspace          | Trace `services/api/src/modules/identity`, `workspaces` and `services/api/src/shared/public`. Are tenant, workspace, membership and caller authority bound independently? Can untrusted body/header/slug data override authenticated or server-resolved authority?                                            |
| App access                      | Compare manifests, `platform` enablement/menu/entitlements and backend guards. A visible menu, active capability or subscription is not operation authorization. Inspect negative paths, revoked membership and cached context.                                                                               |
| Public Booking/OpenBuk          | Trace `booking` controllers/use cases/adapters and public workspace publication. Compare legacy and OpenBuk writers, hold/allocation concurrency, workspace filters, management tokens, idempotency and booking/audit/outbox atomicity. Preserve the existing public journey.                                 |
| Operational people data         | Staff, auth accounts and bookable resources differ. For proposed staff/absence flows inspect every view, tool, export and notification for private reasons versus neutral availability; do not infer those flows are already implemented.                                                                     |
| Decisions and async effects     | Trace `approvals`, `forms`, `workflow` and API-hosted `background`. Does approval bind the current domain command/version? Are retries and out-of-order events scoped and idempotent? Is a queued event incorrectly treated as confirmed delivery?                                                            |
| Files and public content        | Trace `documents`, CMS/website and public routes. Check exact object access, signed URL scope/expiry, publication/ACL changes, rendering and exports. Existing public Knowledge issue #130 does not authorize public employee policies.                                                                       |
| Finance                         | Inspect `expenses`, `invoices`, `purchasing`, `accounting` and their contracts/adapters. Separate claim approval, settlement evidence, posting and money movement. Check exact calculations, transitions, source identity, duplicate/replayed commands and cross-workspace queries.                           |
| AI                              | Trace `ai-copilot`, tool registry/factory/helpers, prompts and owning use cases. Recheck retrieval and execution authority, tenant/workspace fallback, confirmation binding, stale proposals, malicious imported text and output rendering. Preserve separately configured deterministic automation policies. |
| Clients and native integrations | Select the actual Vite/Next.js/Expo surface under `apps/*`. Check private caches/storage, route guards versus backend checks, public checkout and cross-origin/deep-link boundaries. Inspect `apps/eric-wategay` only when the native tax integration is in scope.                                            |
| Delivery                        | Inspect actual CI/deploy/config rather than assumed TruckerPoints machinery. The inspected default/trigger mismatch and historical worker references need runtime facts before a deployed exposure can be claimed.                                                                                            |

Findings need a reachable lower-trust principal, accepted invalid behavior and meaningful impact.
Absence of a proposed catalog module is not itself a security finding. Do not run migrations,
production probes, real provider sends or financial actions as part of a source-only audit.
